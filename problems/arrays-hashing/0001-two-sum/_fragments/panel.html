Plain words

1. Spend a gift card down to exactly zero

You have a gift card worth exactly 11 dollars. The shop has one rule: buy exactly two different items, and their prices must add up to the card's value.

The price tags are listed left to right along a shelf. Your job is to say which two shelf positions to pick.

The story in code words. The shelf is a list of whole numbers called nums. The card's value is target. You return the two positions, called indices, as a list like [4, 5], in any order.

Three promises make the job simpler:

  • Exactly one pair works. You never have to choose between answers.
  • You may not use the same item twice. Two items with the same price are still two items.
  • Prices can be negative or zero here (think of refunds). Do not assume they are positive.

Step through three examples. The lit cells are the answer.

Size: the list holds up to about ten thousand numbers, and each one can be as big as a billion, either sign. Ten thousand numbers means about fifty million pairs. That hints we want something better than trying every pair: aim for O(n) or O(n log n).

Hints

4. Hints, one rung at a time

Hint 1: what are you really asking for each number?

Stand on one number, say x. You do not need any pair. You need one specific value: the one that makes x reach the target. What is that value?

Hint 2: which tool answers "have I seen this value?" fast?

A hash map (a Python dict). It answers "is this value here, and where?" in about one step.

Hint 3: the key step

Walk the list once. For each number, compute the partner it needs, target - x. Ask the map whether that partner has already gone by. If not, store x with its index, and move on. Ask first, store second.

5. The slow way: try every pair

Show the brute force

The obvious plan: take every pair of items, add their prices, and stop at the first pair that matches. The second item always comes after the first, so no pair is tried twice.

Below is the gift card example: nums = [5, 9, 1, 12, 3, 8], target = 11. The grid on the right fills in one cell per pair checked.

The answer sits at the very end, so the search tries all 15 pairs before it finds 3 + 8. Six numbers already cost 15 checks.

Why this is too slowThe number of pairs grows with the square of the list length. Ten thousand numbers give 49,995,000 pairs in the worst case. Doubling the list makes the work four times bigger.

6. The insight: look for the partner, not the pair

Show the pattern insight

For each number x, the partner it needs is target - x. That is one fixed value. So ask the map whether that partner has already gone by.

Analogy: a coat check. Each number you pass hands its coat in and gets a ticket with its position. Later, a number asks "is my partner's coat here?" One glance at the rack answers it. Nobody walks the whole rack.

The value you are looking for is called the complement. The map is seen, from each value to its index. This is the arrays and hashing pattern: trade some memory for speed.

The invariantBefore we look at index i, seen holds every number to the left of i, and nothing else. So a hit always means a different, earlier item.

Same input as the brute force. Watch the map fill up (value : index) and watch each lookup.

6 lookups instead of 15 pair checks. Every number is visited once. When 8 arrives, it needs 3, and 3 is already in the map at index 4.

8. Mental map: how to get here next time

Show the mental map

Read this when a new problem looks a bit like this one. Each step is a question you can ask yourself on a blank page.

  1. Signal"Two items that add up to a target", the answer is positions, the list is not sorted, and n can reach 104 or more.
  2. Ask"Standing on x, what exactly am I looking for?" One fixed value: target - x. And I need its index, not just whether it exists.
  3. PickRule out the forks that do not fit, and keep the one that does.
    • n is tinyAll pairs. O(n^2) is too slow for big lists.
    • sorted input, O(1) memoryTwo pointers. Here the list is unsorted, and sorting loses the indices unless you carry them.
    • only yes or noA set of seen values. Not enough: we must return an index.
    • unsorted, need the partner's indexA dict from value to index, asked before storing.
  4. InvariantBefore index i, seen holds every number to the left of i, so a hit is always a different, earlier item.
  5. StepsEmpty dict. For each index i and number x: compute need = target - x. If need is in the dict, return its index and i. Otherwise store seen[x] = i.
  6. CheckAsk before you store, or x can pair with itself: [3, 4, 2] with target 6 would give [0, 0].
  7. CheckReturn indices, not values, and make sure duplicates work: [0, 4, 0] with target 0 gives [0, 2].
  8. Checkseen must be a dict, not a list, or each lookup scans and the loop is O(n^2) again.

seen = {}An empty dict: value to the index where we saw it. The coat rack.

seen[x] = iOnly now store x, so x can never be its own partner.

Edge cases it handles:

  • Equal values, like [3, 3] with target 6: the first 3 is stored, the second 3 finds it. Answer [0, 1].
  • Negatives and zeros: subtraction works for any sign, so [-4, 7, -1, 12, 5] with target -5 gives [0, 2].
  • Pair at the two ends: the first number waits in the map until the last one asks for it.
  • Huge values: Python integers never overflow, so a billion plus a billion is fine.
Maths

10. Count the work

Step 1: the brute force on the gift card example

With 6 numbers, the first one pairs with 5 others, the next with 4, and so on.

pairs = 5 + 4 + 3 + 2 + 1 = 15 = 6 x 5 / 2 in general: n x (n - 1) / 2 pairs in the worst case

The trace above checked all 15, because the answer was the last pair.

Step 2: the map on the same example

Each number costs one subtraction, one lookup and at most one store. The trace stopped at the 6th number.

lookups = 6 (one per number, at most n)
Step 3: Big-O for time and space
brute force: time O(n^2) extra space O(1) one-pass map: time O(n) extra space O(n) (the map can hold n - 1 numbers) n = 10,000: 49,995,000 pair checks vs 10,000 lookups

A dict lookup is O(1) on average, not in the very worst case. Interviewers accept O(n) average for this. Hidden cost warning: if seen were a list, need in seen would scan it, and you are back to O(n^2).

Step 4: why you cannot do better than O(n)

Any method must read every number at least once. If it skipped one, that skipped number could be the missing partner. So n steps is the floor, and the map reaches it.

Interview

11. What to say in an interview

  1. Clarify. "Is there always exactly one answer? Can values be negative or repeated? Do you want indices or values? May I use the same index twice?"
  2. Example. Walk [5, 9, 1, 12, 3, 8] with target 11 out loud: the answer is 3 + 8, indices 4 and 5.
  3. Brute force. "Try every pair: O(n^2) time, O(1) space. Fine for small n, too slow for ten thousand."
  4. Better idea. "Each number needs one specific partner, target - x. I keep a dict of values seen so far, so each check is O(1)."
  5. Code. One loop. Check the dict first, then store x.
  6. Test. Run the example, then [3, 3] with target 6, to show an item never pairs with itself.
  7. Complexity. "O(n) average time, O(n) extra space."

Follow-up: what if the input list is already sorted?

Use two pointers: one at each end. If the sum is too small, move the left one right. If too big, move the right one left. That is O(n) time and O(1) extra space, no map needed. It is the next pattern (LeetCode 167, Two Sum II).

Follow-up: what if you need all pairs, or values instead of indices, or duplicates are allowed?

Values only: you may sort first, then use two pointers. O(n log n) time, little extra space.

All pairs with duplicates: store a count per value (or a list of indices) instead of one index. Each new x adds count[target - x] pairs, then bumps count[x]. To list distinct value pairs, sort and use two pointers, skipping repeated values.

Check yourself

12. Check yourself

A classmate swapped two lines. They store x before asking for its partner:

def two_sum(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        seen[x] = i                # BUG: x is stored before the check
        need = target - x
        if need in seen:
            return [seen[need], i]
    return []

Predict: what does this buggy version return for nums = [3, 4, 2] and target = 6?

[0, 0], which is wrong. The 3 is stored, then it asks for 6 - 3 = 3, and finds itself. The right answer is [1, 2], because 4 + 2 = 6. On the gift card example the bug stays hidden. It only bites when a number equal to half the target shows up before the real pair is complete.

Show the buggy version step by step

The fix is the order: check first, store second. Then the map only ever holds numbers to the left of i.

Predict: the correct version on nums = [0, 4, 0] and target = 0. What does it return?

[0, 2]. At index 0, it needs 0, and the map is empty, so it stores 0. At index 2, it needs 0 again and finds index 0. The buggy version would return [0, 0] here too.

Predict: on nums = [2, 7, 11, 15] with target 9, how many pair checks does the brute force do, and how many lookups does the map do?

1 pair check and 2 lookups. The brute force gets lucky: the first pair is the answer. Big-O describes how the work grows on bad inputs, not every single run. Try it in the sandbox with the "classic" example.

Recap: Two Sum in one minute

Trigger signals: a pair that adds up to a target, "have I seen this before?", O(n) wanted where O(n^2) is obvious.

Template: seen = {}; for each i, x: need = target - x; if need in seen, return [seen[need], i]; else seen[x] = i. Check before you insert.

Cost: brute force O(n^2) time, O(1) space (15 pair checks on the gift card example). One-pass map O(n) average time, O(n) space (6 lookups). Sorted input: two pointers, O(1) space.
