Plain words

1. Was any ticket used twice?

You guard the door at a school concert. Every guest shows a ticket with a number on it. Tickets are copied sometimes, so the same number might come through twice.

After the night, you get the list of ticket numbers in the order guests arrived. Your job: answer yes or no. Did any number appear more than once?

Analogy: the door guard's notebook. A careful guard writes down each ticket number as it comes in. When a new guest arrives, the guard checks the notebook. If the number is already there, that is a copied ticket. Keep this picture: it is the whole solution in disguise.

Input: a list of whole numbers called nums. Output: True if some value appears at least twice, False if every value is different. A duplicate means the same value at two different positions.

Step through the three examples. Red cells are the repeats. Note that 5 and -5 would be different values.

The limits, and what they hint at

  • The list holds 1 to 100,000 numbers. With 100,000 numbers, checking every pair is about 5 billion checks. Too slow. Aim for O(n) or O(n log n).
  • Each number is between minus one billion and one billion. That range is far too big to use the numbers as positions in a list. Keep that in mind for a follow-up.

4. Hints, one at a time

Hint 1: what do you need to know when you look at a number?

Stand on one number. What single question about the numbers before it would settle everything? Write that question in plain words.

Hint 2: which tool answers that question fast?

The question is "have I seen this value before?". A set answers that in one step on average, no matter how many values it holds. This is the arrays and hashing pattern.

Hint 3: the key step, in words

Walk the list once. For each number: if it is already in the set, stop and answer True. Otherwise, add it to the set. If the walk ends, answer False.

5. The slow but sure way: compare every pair

Show the brute force

The most direct idea: compare each number with every number after it. If any pair matches, answer True. This is the brute force method.

Watch it on [3, 8, 5, 1, 9, 5]. The grid on the right has one cell per pair. An x means "checked, different". An = means "checked, the same".

comparisons on this list12
worst case for 6 numbers (no repeat)15
worst case for 100,000 numbers4,999,950,000

It found the repeat after 12 comparisons. That sounds fine for 6 numbers. But the number of pairs grows with the square of the list length. On this Mac, the pairs method took 1.1 seconds for 10,000 different numbers. Ten times more numbers means about 100 times more work: roughly 2 minutes for 100,000 numbers.

Why it is too slowDoubling the list makes the work four times as large. That is O(n^2), and the limits allow up to 100,000 numbers.

6. Two better ideas, then a race

Show the pattern solution

Idea A: sort first, then look at neighbours

After sorting, equal numbers sit next to each other. So you only need to compare each number with the one just before it. Same list as before:

The sort did 11 comparisons (counted by running Python's sort), then 3 neighbour checks found the pair. Total: 14. Sorting costs about O(n log n), which is far better than O(n^2) on big lists.

Idea B: remember what you have seen (the pattern)

Go back to the door guard's notebook. The one observation: when you reach a number, you only need to know whether it appeared earlier. A hash set answers that in one step on average. It uses hashing to jump straight to where the value would be.

The invariantAn invariant is a fact that stays true every step. Here: before we look at index i, seen holds exactly the values at indices 0 to i - 1, and none of them repeat.

Each number costs one lookup, plus one add if it is new. The repeat 5 is caught on the 6th lookup. The method also has an early exit: it stops the moment it knows.

The race, counted by running the code

On tiny lists the pairs method can get lucky (last row). What matters is the worst case on big lists. Try your own lists in the sandbox race.

What about the one-liner?

return len(set(nums)) != len(nums)

This is correct. A set drops repeats, so it is shorter than the list exactly when a repeat exists. It is O(n) time and O(n) space, like idea B.

The catch: it never stops early. It puts every number into the set first. For the early-repeat list above, the loop does 2 lookups; the one-liner adds all 10 numbers.

100,000 numbers, no repeat: loop4.0 ms
100,000 numbers, no repeat: one-liner1.9 ms
100,000 numbers, repeat at the start: loop0.0001 ms
100,000 numbers, repeat at the start: one-liner1.9 ms

Measured on this Mac with Python's timeit. The one-liner runs inside Python's C code, so it wins when there is no repeat. The loop wins hugely when the repeat comes early. In an interview, both are fine; say which trade-off you picked.

9. The code, line by line

Show the code walk
CodeWhat it means
def contains_duplicate(nums):Takes the list, returns True or False.
seen = set()The guard's empty notebook.
for x in nums:Walk the list once, left to right.
if x in seen:Is this value already written down? One lookup, about one step.
return TrueYes: a repeat. Stop right away (early exit).
seen.add(x)No: write it down, then go on.
return FalseThe walk ended with no repeat, so every value is different.
Common mistakeAdding before checking. If you write seen.add(x) first, then x in seen is always true, and every list looks like it has a repeat. Check first, then add.

Edge cases it handles: an empty list (the loop never runs, returns False), a single number (False), all the same (True on the second number), negative and very large numbers (a set holds any whole number).

Another trapUsing a list instead of a set: x in seen_list searches the whole list each time. That quietly turns the solution back into O(n^2).
Maths (optional)

10. Counting the work

Step 1: pairs, counted for real sizes

With n numbers, the first number is compared with n - 1 others, the next with n - 2, and so on.

pairs = (n - 1) + (n - 2) + ... + 1 = n(n - 1) / 2 n = 8: 8 * 7 / 2 = 28 n = 100,000: 100,000 * 99,999 / 2 = 4,999,950,000

Time O(n^2). Extra space O(1): only two counters.

Step 2: sort, then neighbours
sorting: about n * log2(n) = 100,000 * 16.6 = about 1,660,000 comparisons measured: Python sorted 100,000 random numbers with 1,529,349 comparisons neighbours: at most n - 1 = 99,999

Time O(n log n). Space: sorted(nums) makes a new list, so O(n) extra. nums.sort() sorts in place instead, but it changes the caller's list.

Step 3: the set, and why you cannot beat O(n)
lookups: at most n = 100,000 (one per number) time: O(n) on average space: O(n) for the set (all n values when there is no repeat)

A set lookup is O(1) on average, not guaranteed. Many values landing in the same spot could slow it down. For Python's whole numbers this is rare in practice.

Why O(n) is the best possible: if no number repeats, you must read every number. Any number you skip could have been the repeat.

11. Interview talk track

  1. Clarify. "Can the list be empty? Can numbers be negative? Should I keep the input unchanged?"
  2. Example. "For [3, 8, 5, 1, 9, 5] the answer is True, because 5 repeats."
  3. Brute force. "I could compare every pair. That is n(n - 1)/2 comparisons, O(n^2) time, O(1) space."
  4. Better idea. "I only need to know whether each number appeared before. A set answers that in O(1) on average."
  5. Code. One loop: check, then add. Return True on the first repeat.
  6. Test. Walk the example out loud. Then the empty list and a single number.
  7. Complexity. "O(n) time on average, O(n) extra space. Sorting would use less memory but O(n log n) time."

Follow-ups: (1) what if memory is very tight? (2) what if every number is small, between 0 and k?

(1) Tight memory: sort the list in place, then compare neighbours. Time O(n log n). Extra space O(1) with an in-place sort such as heapsort. Python's list.sort() is in place, but it may borrow up to n/2 temporary slots while merging. Say that the caller's list gets reordered.

(2) Small numbers 0 to k: use a list of k + 1 booleans instead of a set. seen[x] is a true O(1) check with no hashing. Time O(n + k), space O(k). It only pays off when k is small; here values reach one billion, so it would not fit.

12. Check yourself

Predict: the set version gets an empty list. What does it return, and how many lookups does it make?

False with 0 lookups. The loop body never runs, so the last line returns False. No numbers means no repeats.

Predict: someone promises the list is already sorted. What is the best method now, and what does it cost?

Skip the sort and compare neighbours only. Time O(n), extra space O(1). That beats the set on memory.

Predict: the question changes to "does any value appear at least 3 times?". Does a set still work?

Not alone: a set only says "seen or not". Use a dictionary of counts instead (value to how many times so far), and return True when a count reaches 3. Still O(n) time and O(n) space.

Glossary

duplicate
The same value at two different positions in the list.
brute force
The simplest correct method, usually trying every possibility.
O(n), O(n^2), O(n log n)
How the work grows with the list length n: in step, with the square, or a little faster than in step.
hash set
A collection of unique values that answers "is x in here?" in about one step.
hashing
Turning a value into a storage position, so a lookup jumps straight there.
invariant
A fact that stays true at every step of a loop. Here: seen holds exactly the values already walked past.
early exit
Stopping as soon as the answer is known.
in place
Changing the input itself instead of building a copy.
average case
The typical cost, not the unluckiest possible one.

Recap: the pattern in one minute

Pattern: arrays and hashing. Trade memory for time: remember what you have seen, so each later question is one lookup.

Trigger signals: "have I seen this before?", repeats, counting, O(n) wanted where two nested loops are obvious.

Template: seen = set(); one pass; check before you add; return early when the answer is known.

Cost: pairs O(n^2) time; sort O(n log n) time; set O(n) time on average and O(n) space.
