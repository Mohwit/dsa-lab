1. Take the best move now, and never look back

A greedy method makes one choice at each step. It picks whatever looks best right now. It never undoes a choice.

That makes greedy code short and fast: usually one pass, sometimes after a sort. The hard part is not the code. The hard part is being sure the choice is safe.

Analogy: a cashier giving change. You are owed 41 cents. The cashier grabs the biggest coin that still fits (25), then the biggest that fits again (10), then 5, then 1. Four coins, and no thinking ahead. With normal coins this is always the fewest. With strange coins it can go wrong, and section 2 lets you break it.

Here is greedy in its most famous costume. You get a list of daily gains and losses. Which unbroken run of days has the biggest total?

Rule to rememberA running total that has gone below zero can only drag the next number down. Drop it and start again. That one safe choice turns an O(n2) search into one pass.

2. Prove it, or it is DP: break greedy on purpose

Greedy feels right far more often than it is right. So the rule in interviews is simple: either you can say why the choice is safe, or you treat the problem as dynamic programming.

Try it: the coin machine

Pick a coin set and slide the amount. The top row is the cashier's greedy pick (biggest coin first). The bottom row is the true fewest coins, found by checking every amount from 1 up (dynamic programming). When greedy loses, its row turns orange.

The page computes both rows live. measure.py prints the same: with coins 1, 3, 4 and amount 6, greedy pays 4 + 1 + 1 (3 coins) but 3 + 3 (2 coins) is best. Over amounts 1 to 40, greedy loses 0 times with 1, 5, 10, 25; 9 times with 1, 3, 4; 9 times with 1, 7, 10 (first at 14); and 6 times with 1, 10, 25 (first at 30).

Before you slide: with coins 1, 10, 25, what does greedy pay for 30, and what is best?

Greedy: 25 + 1 + 1 + 1 + 1 + 1 = 6 coins. Best: 10 + 10 + 10 = 3 coins. Taking the 25 felt great and then left 5 that only pennies can pay. That is the whole danger of greedy in one example.

How to prove a greedy choice is safe: the swap argument

The standard proof is called an exchange argument. In plain words:

  1. Imagine someone hands you a perfect answer.
  2. If its first choice differs from greedy's, swap in greedy's choice.
  3. Show that the swap breaks nothing and costs nothing.
  4. Repeat. You turn the perfect answer into the greedy answer without ever making it worse, so greedy was perfect too.
Swap works: meetings by earliest endYou want the most meetings in one room. A perfect plan starts with some meeting M. Swap M for the meeting that ends first. It ends no later than M, so everything after M still fits. Same count, still valid. So "earliest end first" is safe.
Swap fails: coins 1, 3, 4 for 6The perfect answer is 3 + 3. Greedy wants to start with a 4. Swap a 3 for the 4: now 4 + 3 = 7 is too much, and 4 + 1 + 1 needs an extra coin. The swap costs something, so the proof breaks, and greedy really is wrong here.
Rule to rememberBefore you trust a greedy idea, spend one minute hunting for a small counterexample. If you find one, switch to DP. If you cannot, say the swap argument out loud.

4. Mental map: from a problem statement to greedy code

Read this when you meet a new problem and wonder "could greedy work here?".

  1. Signal"Minimum number of", "maximum number of", "can you reach", "is it possible", an unbroken run with the best sum, or a list of intervals. Often n is up to 105, so O(n) or O(n log n) is expected.
  2. AskIs there one choice I can make right now that I will never regret? Can I describe everything to my left with one or two numbers?
  3. Pick the variantMatch the tell-tale sign.
    • best unbroken run, a balance that dipsRunning sum, restart when it hurts (Kadane, Gas Station)
    • can you reach, fewest jumpsReach pointer: track the farthest spot (Jump Game I and II)
    • most meetings, fewest arrows, intervalsSort by end, take each one that fits
    • match big with small, build groupsSort first, then take in order (Hand of Straights, Assign Cookies)
    • a range of possible countsTrack a low and high bound (Valid Parenthesis String)
    • you found a counterexampleNot greedy: dynamic programming (Coin Change, 0/1 knapsack)
  4. InvariantAfter each step, your few variables (cur, reach, end) hold everything that matters about the part already scanned, and no better answer was thrown away.
  5. StepsSort if the order matters (by end time, by size). Start the state variables. One loop: update the state with the safe choice, check the stop condition. Return the state.
  6. CheckTry two or three tiny inputs by hand, including a counterexample hunt. Then: all negative numbers, a zero you cannot jump past, intervals that only touch, a single item, and the sort key.
Interview tipSay the greedy rule in one sentence ("always take the meeting that ends first"), then say why it is safe in one more. Interviewers care about the second sentence more than the code.

5. Four templates cover most greedy problems

Template A: running sum, restart when it hurts

Maximum subarray, best day to sell, gas station. This is the scan you raced in section 1.

CodeWhat it means
def max_subarray(nums):Best total of any unbroken run. The list has at least one number.
best = nums[0]Start from a real number, not 0, so an all-negative list still works.
cur = 0The best total of a run that ends at the current number.
for x in nums:One pass, left to right.
cur = max(x, cur + x)The greedy choice: extend the run, or restart at x if the old run only drags x down.
best = max(best, cur)Remember the best run seen so far.
return bestO(n) time, O(1) memory.

Template B: the reach pointer

Each number says how far you may jump from that spot. Can you get to the last spot? Keep one number: the farthest spot you can reach so far.

CodeWhat it means
def can_jump(nums):True if the last index is reachable from index 0.
reach = 0So far you can only stand on index 0.
for i, step in enumerate(nums):Walk every spot in order.
if i > reach:Can I even stand here? If i is past the reach, nothing before could get here.
return FalseStuck: a gap no jump crosses.
reach = max(reach, i + step)The greedy update: push the reach as far as this spot allows.
return TrueEvery spot was reachable, including the last.

Watch the reach (blue zone) grow, with the code walk above as your guide. Switch between a list you can finish and one with a gap.

measure.py: can_jump([3, 1, 0, 2, 0, 1]) is True after 6 checks; can_jump([2, 1, 0, 3, 1]) is False at the 4th check, because index 3 sits past reach 2. The fewest-jumps version (Jump Game II) on the first list returns 2.

Template C: sort by end, take each one that fits

The most meetings in one room, the fewest intervals to remove, the fewest arrows. Finish early to leave the most room for the rest.

CodeWhat it means
def max_meetings(intervals):Each interval is [start, end]. Touching (one ends at 5, the next starts at 5) is allowed.
count, end = 0, float("-inf")Nothing booked yet; the room is free from the start of time.
for s, e in sorted(intervals, key=lambda iv: iv[1]):The sort is the greedy rule: earliest end first. This costs O(n log n).
if s >= end:Does it start after the last booked meeting ends?
count += 1Book it.
end = eThe room is now busy until e.
return countThe most meetings that fit.

measure.py: on [[5, 9], [1, 3], [6, 8], [2, 5], [8, 10], [4, 6]] the scan books 4 meetings after 6 checks. Trying every subset agrees (4), but it tries 64 subsets.

Template D: fewest jumps, in levels

Jump Game II. Think of rings: every spot you can reach with one jump, then with two, and so on. When you walk off the end of the current ring, you must spend a jump.

CodeWhat it means
def min_jumps(nums):Assumes the last index can be reached.
jumps, end, far = 0, 0, 0end is the edge of the current ring; far is the farthest the next ring reaches.
for i in range(len(nums) - 1):Stop before the last spot: you never jump from it.
far = max(far, i + nums[i])Same reach update as Template B.
if i == end:At the edge of the ring: one more jump is needed.
jumps += 1; end = farSpend it, and the next ring ends at far.
return jumpsO(n) time, O(1) memory.
Rule to rememberGreedy code is a loop with one or two state variables, often after a sort. If your loop needs a table of past answers, you are writing DP.
Pattern words

6. Spot the pattern: is greedy safe here?

Read each made-up task. Decide: greedy or not, and which variant. Then reveal.

A. A lecture hall gets requests with a start and an end time. Accept as many talks as possible with no overlap.

Greedy, Template C. Signal: intervals and "as many as possible". Sort by end and take each talk that fits. The swap argument from section 2 proves it.

B. A country uses coins of 1, 6 and 9. Pay a given amount with the fewest coins.

Not greedy: DP. It looks just like the cashier, but the coin set is unusual. Amount 12: greedy pays 9 + 1 + 1 + 1 (4 coins), while 6 + 6 is 2. Any coin set you did not prove safe means DP.

C. A frog stands on stone 0. Each stone's number is the longest hop allowed from it. Can the frog reach the last stone?

Greedy, Template B. Signal: "can you reach". Keep the farthest reachable stone. You never need to know which path, only how far any path gets.

D. A trader has a list of daily profit changes. Find the best total over a stretch of back-to-back days.

Greedy, Template A (Kadane). Signal: best unbroken run. Restart whenever the running total is worth less than today alone.

E. A hiker's backpack holds 10 kg. Each item has a weight and a value and must be taken whole or left. Maximise the value.

Not greedy: DP (0/1 knapsack). "Best value per kg first" breaks: items (6 kg, 30), (5 kg, 20), (5 kg, 20) with 10 kg. Greedy takes the 6 kg item (5 per kg) and then nothing else fits: 30. Two 5 kg items give 40. If items could be cut into pieces, greedy by value per kg would be safe.

F. Children each need a cookie of at least a certain size. You have a bag of cookies of various sizes. Feed as many children as you can.

Greedy, sort then take. Sort both lists. Give each child, least hungry first, the smallest cookie that is big enough. A bigger cookie is never better spent on a less hungry child.

Trigger signals"Most / fewest / can you reach", intervals, best unbroken run, a balance that dips, and a choice you can defend with a swap. Warning signs for DP: odd coin sets, items taken whole, and "count the number of ways".

7. Four classic traps

Trap 1: greedy where only DP is safe

The cashier rule on a coin set nobody proved safe.

def fewest_coins(coins, amount):          # wrong for some coin sets
    count = 0
    for c in sorted(coins, reverse=True):
        count += amount // c
        amount %= c
    return count

Fails on coins = [1, 3, 4], amount = 6: it returns 3 (4 + 1 + 1), the answer is 2 (3 + 3). Fix: DP over amounts, dp[a] = min(dp[a - c] + 1 for c in coins if c <= a). It is O(amount x coins): 120 checks for amount 40 and 3 coins.

Trap 2: sorting intervals by start

Sorting by start feels natural, but an early, very long meeting blocks everything.

for s, e in sorted(intervals):            # wrong: sorts by start
    if s >= end:
        count += 1; end = e

Fails on [[1, 10], [2, 3], [4, 5]]: it books [1, 10] and nothing else fits, so 1. Sorted by end it books [2, 3] and [4, 5]: 2. Fix: key=lambda iv: iv[1].

Trap 3: Kadane that assumes the answer is at least 0 
best = 0; cur = 0                           # wrong start
for x in nums:
    cur = max(0, cur + x)                    # an empty run is not allowed
    best = max(best, cur)

Fails on [-3, -1, -2]: it returns 0, the empty run. The answer is -1. Fix: best = nums[0] and cur = max(x, cur + x), as in Template A.

Trap 4: pushing the reach from a spot you cannot stand on 
reach = 0
for i, step in enumerate(nums):
    reach = max(reach, i + step)             # wrong: never asks "is i reachable?"
return reach >= len(nums) - 1

Fails on [0, 1]: index 1 is out of reach, yet its jump still pushes the reach to 2, so it returns True. The answer is False. Fix: check if i > reach: return False before the update.

All four wrong answers and their fixes are printed by measure.py (section "5. Traps").

Rule to rememberHunt for a counterexample, sort by the right key, never assume the answer is at least 0, and only act from states you can actually be in.

8. Complexity: one pass, plus the sort

Slide the list size. Both racers do one operation per tick. Every run must be added up by the slow way, so it has no lucky early exit.

Step 1: where 55 and 500500 come from

A run starting at index 0 can end at n places. A run starting at index 1 can end at n - 1 places. And so on down to 1:

n + (n - 1) + ... + 1 = n x (n + 1) / 2

For n = 10 that is 10 x 11 / 2 = 55. For n = 1000 it is 1000 x 1001 / 2 = 500500. That is O(n2). The greedy scan touches each number once: O(n).

Step 2: the hidden cost is the sort

Templates A, B and D are one pass: O(n) time and O(1) extra memory. Template C sorts first, and a sort costs about n x log2(n) comparisons:

n = 1000: 1000 x log2(1000) = about 9966 comparisons for the sort then 1000 checks for the scan

So the sort dominates: O(n log n) time. Python's sorted also builds a new list: O(n) memory (list.sort() sorts in place).

Step 3: what greedy saves compared with DP and brute force

The coin DP checks every coin for every amount: O(amount x coins), for example 40 x 3 = 120 checks. Trying every subset of meetings is O(2n): 64 subsets for 6 meetings, about a million for 20. A correct greedy rule replaces all that with one pass.

Rule to rememberGreedy is O(n) if you scan, O(n log n) if you sort first, and O(1) extra memory apart from the sort.

Check yourself

10. Your lesson's questions

Q1. Template A runs on [-3, -1, -2]. What does it return, and how many steps does it take?

-1, after 3 steps. Every number restarts the run (each old run is negative), and the best single number is -1. measure.py prints (-1, 3). The trap version would return 0.

Q2. Template B runs on [1, 0, 1]. What does it return, and at which check does it stop?

False, at the 3rd check. Index 0 pushes reach to 1. Index 1 has a 0, so reach stays 1. Index 2 is past reach 1, so the frog is stuck. measure.py prints (False, 3).

Q3. You need the most non-overlapping meetings. A friend sorts by length, shortest first. Find a small input where that loses.

One example: [[1, 5], [4, 7], [6, 10]]. Shortest first books [4, 7] (length 3), which overlaps both others: 1 meeting. Earliest end books [1, 5] and [6, 10]: 2 meetings. A short meeting in the middle can block two. This is how you test a greedy rule: hunt for a tiny counterexample.

Glossary: new words from this lesson

greedy
Build the answer one choice at a time, always the best-looking choice now, never undone.
local vs global best
Best for this step vs best overall. Greedy works when the first always leads to the second.
exchange argument
Swap a perfect answer's choice for greedy's, show nothing breaks or gets worse, repeat.
greedy-choice property
Some best answer contains the greedy choice.
optimal substructure
After a choice, the rest is a smaller copy of the same problem.
counterexample
One input where a method gives the wrong answer. One is enough to reject it.
dynamic programming (DP)
Solve every smaller version once, store the answers, build the big answer from them.
running sum
A total you keep updating as you scan.
Kadane
Maximum subarray in one pass: extend the run or restart at the current number.
reach
The farthest index you can get to so far.
invariant
A fact about your variables that stays true after every step.

Recap: the pattern card in one minute

Idea: make the best-looking choice now and never undo it, but only after you can say why it is safe (the swap argument). If a tiny counterexample breaks it, use DP.

Signals: "most / fewest / can you reach", intervals, best unbroken run, a balance that dips, n up to 105.

Templates: A cur = max(x, cur + x); B if i > reach: return False then reach = max(reach, i + step); C sort by end, take if s >= end; D count rings with end and far.

Cost: O(n) for a scan, O(n log n) with a sort, O(1) extra memory. Brute force over runs is O(n2): 500,500 run totals against 1000 steps at n = 1000.

Traps: unproved coin sets (1, 3, 4 for 6), sorting by start, best = 0 with all-negative input, pushing the reach from a spot you cannot reach.

In the sandbox, type your own list and run the running-sum scan or the reach pointer. Try an all-negative list, and a jump list with a zero in a bad place.
