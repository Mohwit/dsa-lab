1. Count how the work grows when the input doubles

"Is my code fast?" is the wrong question. Fast on 10 items says nothing about 10 million items.

The useful question is: if the input doubles, what happens to the work? Does it stay the same, grow by one step, double, or explode?

Analogy: finding a word in a paper dictionary. You could flip every page from the front until you hit the word. Or you could open in the middle, see that your word comes later, and throw away the first half. Then open the middle of what is left, and so on. A dictionary twice as thick costs the page-flipper twice the work. It costs the middle-opener just one more look.

Try it: the same sorted list, two ways

The list holds 16 sorted numbers, and we look for 97. Press Step or Play on each player.

Slow: page by page. Check index 0, then 1, then 2, until the number turns up.

Fast: open in the middle. Look at the middle. Too small? Throw away the left half. Too big? Throw away the right half.

page by page- checks
open in the middle- checks

Both counts come from running the code, here and in measure.py: 14 checks against 3. On a sorted list of 1,000,000 numbers the worst case is 1,000,000 checks against 20.

Rule to rememberDo not time your code with a stopwatch. Count its steps for an input of size n, and ask how that count grows as n grows.

2. The growth race: six shapes of work

Almost every algorithm you will meet has one of six growth shapes. The labels are written in Big-O.

LabelNameTypical code
O(1)constantone dict lookup, read a[i]
O(log n)logarithmichalve the range each step (binary search, fast power)
O(n)linearone loop over the items
O(n log n)linearithmicsorting; a loop around a halving loop
O(n2)quadratica loop inside a loop: every pair
O(2n)exponentialtry keep-or-skip for every item: every subset

Try it: drag n and watch the counters

Each lane runs a small loop of that shape and counts its steps. The bars use a log scale (each grid line is 10 times the one before), or the 2n bar would not fit on your screen.

The race gives every lane the same budget of steps per tick, and the budget grows by the same factor each tick. Watch which lanes finish while the last one is still running.

Predict: n goes from 10 to 20. By what factor does each lane's step count grow?

From measure.py, counting the same loops:

O(1)            1 ->           1   x1.0
O(log n)        4 ->           5   x1.2   # one more halving
O(n)           10 ->          20   x2.0
O(n log n)     40 ->         100   x2.5
O(n^2)        100 ->         400   x4.0
O(2^n)      1,024 ->   1,048,576   x1,024.0

Doubling n adds one step to log n, doubles n, quadruples n2, and squares 2n.

What this means for a real limit

A plain Python loop on this laptop (Apple M5, Python 3.10.20) does about 62 million simple steps per second, measured by measure.py. So:

# == 2b. steps, and seconds at the measured loop speed ==
n = 10^5, O(n^2)        10,000,000,000 steps ~ 161 s      # too slow
n = 10^5, O(n log n)         1,700,000 steps ~ 0.027 s    # fine
n = 20,   O(2^n)             1,048,576 steps ~ 0.017 s    # fine
n = 40,   O(2^n)     1,099,511,627,776 steps ~ 17,754 s   # about 5 hours
Read the limit firstThe input limit in a problem tells you the Big-O you need. n up to 20: 2n is fine. n up to a few thousand: n2 is fine. n up to 105 or 106: aim for n log n or n. n up to 109: you need log n, or a formula.

3. Recursion: a function that hands a smaller job to itself

Analogy: Russian nesting dolls. To count the dolls, open the outer one and ask: "how many dolls are inside this smaller one?" That is the same question on a smaller doll. You stop at the tiny solid doll that does not open. That solid doll is the base case.

Every recursive function has two parts. The base case answers the tiniest input directly. The recursive case shrinks the job, calls itself, and uses the answer.

Watch the call stack grow and shrink

Python keeps one note per unfinished call on the call stack. Each note says "I am waiting for an answer". Step through factorial(4) and watch the pile.

measure.py agrees: factorial(4) returns 24 after 4 calls, and at most 4 calls wait on the stack at once. Those 4 waiting notes are memory: recursion depth counts as space.

Two calls per call: the naive Fibonacci tree

Fibonacci numbers start 0, 1, and each next one is the sum of the two before. So fib(n) = fib(n - 1) + fib(n - 2). That is two calls inside every call. Each circle below is one call, labelled with its n. Orange circles are calls that repeat work done before.

Naive: recompute everything. fib(5) asks for fib(4) and fib(3), and fib(4) asks for fib(3) again.

Memo: write each answer down. Before computing fib(k), look in a dict. Found? Use it and stop.

naive fib(5)- calls
memo fib(5)- calls
naive fib(30)2,692,537 calls
memo fib(30)59 calls

In naive fib(5), fib(3) runs 2 times, fib(2) 3 times and fib(1) 5 times (from measure.py). The waste grows fast: at n = 30 it took 0.41 s naive against 9 microseconds with the memo on this laptop.

Rule to rememberThe cost of a recursion is (number of calls) x (work per call). Its extra space is the deepest the stack gets. One call per call gives a chain; two calls per call gives a tree that doubles each level, unless a memo cuts off the repeats.

5. Mental map: from a blank page to working code

Use this checklist on every problem, not only the recursive ones. It is how you pick an approach before you write a line.

  1. SignalLook at the limits: n up to 20, 103, 105 or 109. For recursion, look for a job that contains a smaller copy of itself: "the answer for n uses the answer for n - 1 or n / 2", nested shapes, trees, "all ways to ...".
  2. Ask"If the input doubles, how much more work does my idea do?" and "Can I solve a smaller version and grow it into the full answer?"
  3. PickChoose the shape of recursion by how the job shrinks. The clue for each sits in yellow.
    • answer(n) uses answer(n - 1)Linear recursion: one call per call, a chain. O(n) calls, O(n) stack. Factorial, sum of a list. Often a loop is simpler.
    • shrink from both endsTwo-ended recursion: solve(l + 1, r - 1). n / 2 calls. Reverse a string, palindrome check.
    • answer(n) uses answer(n / 2)Halving recursion: one call on half the input. O(log n) calls. Fast power, binary search.
    • two or more calls, same arguments repeatBranching recursion with a memo: O(2n) calls without it, one call per distinct argument with it. Fibonacci, climbing stairs.
    • "all subsets / all orders"Branching recursion without repeats: the 2n is real, so n must be small (about 20). This is backtracking, a later lesson.
  4. InvariantTrust the smaller call. Assume solve(smaller) already returns the right answer, and only check that your one step turns it into the right answer for the full input. This "leap of faith" is induction.
  5. StepsWrite the base case first. Then the recursive case: shrink the input, call once (or twice), combine. Then count: calls x work per call for time, deepest chain for space.
  6. CheckDoes every call move towards the base case, for every input, including 0, 1 and negatives?
  7. CheckIs the depth below about 1000? Python stops deeper recursion with a RecursionError. A chain over 105 items needs a loop.
  8. CheckHidden costs: a slice s[1:] copies the list on every call, and calling the same half twice undoes the halving.
Rule to rememberBase case, smaller call, combine. Then count calls x work, and the depth.

Template A: the recursion skeleton

CodeWhat it means
def factorial(n):The job: n x (n - 1) x ... x 1.

Template B: halving (fast power)

x13 = x6 x x6 x x. So one call on n // 2 is enough, then square it, and multiply by x once more if n is odd.

CodeWhat it means
def power(x, n):x to the power n, for any whole n.
  if n < 0:A negative power?
    return 1 / power(x, -n)Flip it: 2-2 = 1 / 22.
  if n == 0:Base case check.
    return 1Anything to the power 0 is 1.
  half = power(x, n // 2)One call on half the power. Store it: never call it twice.
  result = half * halfSquare the half answer.
  if n % 2 == 1:Odd n lost one x when we floored n / 2 ...
    result = result * x... so put it back.
  return resultAbout log2(n) calls in total.

Step through power(2, 13). The stack shows the chain of halvings: 13, 6, 3, 1, 0.

From measure.py: power(2, 13) = 8192 with 5 calls and 7 multiplications. A plain loop needs 13. For n = 109, power makes 31 calls; the loop makes 1,000,000,000 multiplications.

Template C: memoization

CodeWhat it means
def fib(n, memo):memo is a dict shared by every call.
  if n in memo:Already solved?
    return memo[n]Reuse it. This line cuts every repeat branch.
  if n <= 1:Base cases ...
    return n... fib(0) = 0, fib(1) = 1.
  memo[n] = fib(n - 1, memo) + fib(n - 2, memo)Solve once, write it down.
  return memo[n]Each n is computed once: 2n - 1 calls, O(n) time and space.

In Python you can get the same effect with from functools import cache and @cache above a plain def fib(n).

Rule to rememberHalve to get log n. Memo to turn a tree of repeats into one call per distinct argument.

Pattern words

7. Spot the pattern: which shape, which cost?

For each made-up task, say whether recursion is the natural tool, which shape (chain, two ends, halving, tree with memo), and the Big-O. Then reveal.

A. Compute 3 to the power 1,000,000,000, keeping only the last 9 digits.

Halving. Signal: a power that big, n up to 109. Fast power makes about 31 calls; a loop would make a billion multiplications. Take the remainder after each multiply.

B. A robot climbs a staircase of n steps, 1 or 2 steps at a time. In how many different ways can it reach the top? n is at most 45.

Tree with a memo. ways(n) = ways(n - 1) + ways(n - 2), the same shape as Fibonacci. Without a memo the calls grow like 2n; with it, O(n).

C. Reverse a list of characters in place, using recursion on the two ends.

Two ends. Swap s[l] and s[r], then recurse on l + 1, r - 1; stop when l >= r. O(n) time, but O(n) stack: about n / 2 waiting calls.

D. A log file has 2,000,000 lines. Count the lines that contain the word "error".

Not recursion. It looks like "count of the rest plus this line", but a chain of 2,000,000 calls blows Python's limit of 1000. A plain loop: O(n) time, O(1) space.

E. List every way to choose a team from 12 players (any size, including empty).

Tree, and the 2n is real. Each player is "in" or "out": 212 = 4096 teams to list. No memo helps, because every leaf is a different answer. Fine because n is small. (Backtracking, later.)

F. A sorted list of prices; many shoppers each ask "what is the total of prices from position 3 to position 900?"

Not halving. "Sorted" tempts you to binary search, but the question is about a sum of a stretch, not finding a value. Running totals answer each question in O(1): that is the prefix sums lesson.

Trigger signalsA smaller copy of the same job inside the job; n or a power up to 109 (halve); the same arguments asked again and again (memo); and always: the input limit tells you the Big-O you can afford.

8. Four classic traps

Trap 1: a base case that some inputs skip past 
def fact_bad(n):
    if n == 1:          # 0 never equals 1 on the way down
        return 1
    return n * fact_bad(n - 1)

fact_bad(0)  # -> RecursionError: maximum recursion depth exceeded in comparison

fact_bad(0) calls -1, -2, -3 ... and never meets 1. Fix: if n <= 1. Test the base case with 0, 1 and a negative.

Trap 2: forgetting that the stack is memory

A recursive reverse of a string swaps the ends and recurses on the middle. It looks like O(1) space. It is not: every call waits on the stack.

# == 5. Trap: recursion depth (limit = 1000) ==
reverse_rec on 10 chars:   ok, max depth = 6
reverse_rec on 1500 chars: ok, max depth = 751
reverse_rec on 5000 chars: RecursionError (needed depth 2501)

Fix: say "O(n) stack space" out loud, and for long inputs use a loop with two pointers. Raising the limit with sys.setrecursionlimit is a patch, not a cure.

Trap 3: calling the half twice 
return power(x, n // 2) * power(x, n // 2)   # looks the same, costs far more

Two calls per call rebuild the doubling tree, so the halving buys nothing back.

# == 5. calls: half computed twice vs stored once ==
n =      10: calls =        31   power calls = 5
n =    1000: calls =     2,047   power calls = 11
n = 1000000: calls = 2,097,151   power calls = 21

Fix: half = power(x, n // 2) once, then half * half.

Trap 4: a slice hidden in every call 
def total(nums):
    if not nums: return 0
    return nums[0] + total(nums[1:])   # nums[1:] copies the rest

n calls, but each copies up to n items: O(n2). measure.py counted 404,550 copied items for a list of 900. Fix: pass an index, total(nums, i + 1), which copies nothing.

Rule to rememberEvery input must reach the base case. Count the stack as space. Store the half. Pass indices, not slices.

9. Complexity: count it, then name it

Step 1: counting the six shapes at n = 1000

Using the same loops as the race (from measure.py): O(1) is 1 step; O(log n) is 10 halvings; O(n) is 1000; O(n log n) is 1000 x 10 = 10,000; O(n2) is 1,000,000. O(2n) has 302 digits, so it is never run.

Halving counts: 1000, 500, 250, 125, 62, 31, 15, 7, 3, 1. That is 10 halvings, and log2(1000) is about 9.97.

Step 2: recursion = calls x work per call
factorial: n calls x O(1) = O(n) time, depth n = O(n) space
power: about log2(n) + 2 calls x O(1) = O(log n) time and space
naive fib: calls(n) = calls(n - 1) + calls(n - 2) + 1

That last line makes naive fib's call count grow like the Fibonacci numbers themselves, roughly 1.6n: 177 calls at n = 10, 21,891 at n = 20, 2,692,537 at n = 30. Each step of 10 in n multiplies the count by about 123 (123.7 and 123.0). People often say O(2n): it is a safe upper bound.

The deepest chain is fib(n), fib(n - 1), ..., fib(1): n calls (depth 5 for fib(5) in measure.py). So naive fib is exponential in time but only O(n) in space.

Step 3: why the memo makes it O(n)

With the memo, each fib(k) for k from 2 to n does real work once and makes 2 calls. Every other call is a quick lookup. So calls = 1 + 2(n - 1) = 2n - 1: 9 at n = 5, 59 at n = 30. Time O(n), space O(n) for the dict plus O(n) for the stack.

11. Your lesson's questions

Q1. A sorted list holds 1,000,000 numbers. You search for a number smaller than all of them. How many middle checks does halving make?

19. Each check halves what is left, and log2(1,000,000) is about 20. measure.py prints 19 for this search; the worst target needs 20. Page by page would need 1,000,000.

Q2. How many calls does factorial(6) make, and how deep does the stack get? How many calls does naive fib(6) make, and memo fib(6)?

factorial(6): 6 calls, depth 6, value 720. Naive fib(6): 25 calls (15 for fib(5) + 9 for fib(4) + 1). Memo fib(6): 11 calls (2 x 6 - 1). All from measure.py.

Q3. Trace power(3, 5) from Template B. How many calls and how many multiplications?

4 calls (n = 5, 2, 1, 0) and 5 multiplications: 1 x 1 x 3 = 3 for n = 1, 3 x 3 = 9 for n = 2, 9 x 9 x 3 = 243 for n = 5. Try it in the sandbox to check.

Recap: the pattern card in one minute

Idea: count steps, not seconds, and ask what happens when n doubles. Recursion solves a job by trusting a smaller copy of it.

Signals: the input limit (20: 2n ok; 105: n log n; 109: log n); a job that contains a smaller copy of itself; the same arguments repeating.

Templates: if base: return answer, then combine(solve(smaller)). Halving: half = power(x, n // 2) once. Memo: if n in memo: return memo[n].

Cost: calls x work per call; space = deepest chain. factorial: O(n) and O(n). power: O(log n). naive fib: 2,692,537 calls at n = 30; memo fib: 59.

Traps: a base case some inputs skip; the stack is memory (limit 1000); calling the half twice; slicing in every call.

In the sandbox, run each recursion on your own n. Watch the stack height and the call count, and find the n where naive fib needs more than 100 calls.
