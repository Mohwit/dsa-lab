1. Remember what you have seen, so you never search twice

Many problems hide the same small question: "have I seen this before?" You ask it once for every item in a list.

The slow way answers it by looking back through everything again. The fast way keeps a memory that answers it in one glance.

Analogy: a coat check. You hand over your coat and get a ticket. Later, the attendant does not walk the whole rack to find it. The ticket number says exactly which hook to look at. Asking "is my coat here?" takes one glance, no matter how many coats hang there.

Here is the question in its simplest costume. You get a list of numbers. Does any number appear twice?

Try it: the same list, two ways

Press Step or Play on each player. The list is [5, 2, 8, 1, 9, 2].

Fast: the seen-it scan. Walk the list once. For each number, glance at the memory (the chips). Not there? Add it.

Slow: compare every pair. Take each number and compare it with every number after it. The grid lights one cell per comparison.

seen-it scan- steps
compare every pair- comparisons

Both counts come from running the two methods on this list (in the page and in measure.py, which prints 6 steps and 9 comparisons). On six numbers the gap is small. The next section shows what happens when the list grows.

Rule to rememberSpend a little memory to save a lot of time. Keep what you have seen in a set or a dictionary, and every later question is one lookup.

2. How to measure "fast": count the work as the list grows

A stopwatch depends on your laptop. So instead we count steps: how many basic actions does the method do for a list of n items?

What matters is how that count grows when n grows. That growth is called Big-O.

O(n): linearThe seen-it scan looks at each item once. Ten times more items means ten times more steps.
O(n2): quadraticComparing every pair does about n x n / 2 comparisons. Ten times more items means about a hundred times more work.

Try it: an operation race

Both racers do one operation per tick, at the same speed. The lists have no repeats, so both must check everything (the worst case). Pick a size, then start the race.

list size n10
seen-it steps10
pair comparisons45
pairs / steps4.5x

The page runs both methods with a counter on lists of 0, 1, 2, ... n-1. The bar scale is the pair count, so at n = 1000 the teal bar is almost invisible.

measure.py counts the same thing in Python:

# == 2. Operation race, no repeats (worst case: both scan everything) ==
n =   10: set scan steps =    10   pair comparisons =      45   ratio = 4.5x
n =  100: set scan steps =   100   pair comparisons =    4950   ratio = 49.5x
n = 1000: set scan steps =  1000   pair comparisons =  499500   ratio = 499.5x
Step 1: where 45, 4950 and 499500 come from

The first number is compared with the n - 1 after it. The second with n - 2. The last with none. Add them up:

(n - 1) + (n - 2) + ... + 1 + 0 = n x (n - 1) / 2

For n = 10 that is 10 x 9 / 2 = 45. For n = 1000 it is 1000 x 999 / 2 = 499500. The "/ 2" does not change the shape of the growth, so Big-O drops it: O(n2).

Step 2: why a lookup in a set counts as one step

A set does not search its items. It turns the item into a number (the hash) and jumps straight to one slot, like the coat ticket. So "is x in the set?" costs about the same for 10 items or 100000 items.

On this laptop (Apple M5, Python 3.10.20) measure.py timed one set lookup at 25.3 ns with 104 items and 26.8 ns with 105 items: ten times more items, almost the same time. That is O(1) on average.

Rule to rememberInputs of 105 items rule out O(n2): that is about 5 billion comparisons. When a problem's limit is that big, look for an O(n) idea, and a set or dictionary is the first thing to try.

4. Mental map: from a blank page to working code

Read this list top to bottom when a new problem lands in front of you. It is the "how do I start" checklist for the whole pattern.

  1. SignalThe statement asks "is there a repeat?", "how many of each?", "which items belong together?" or "is there a partner that adds up to a target?". Or the input is up to 105 items and the obvious idea compares every pair.
  2. Ask"For each item, what single question do I keep asking about the items before it?" If that question is a lookup (seen it? how many? which group? where is my partner?), a hash map answers it in one glance.
  3. PickChoose the variant by what the lookup must return. The clue for each sits in yellow.
    • only "seen it before?"Seen-set membership: seen = set(), ask x in seen, then seen.add(x). Contains Duplicate.
    • "how many of each?"Counting: Counter(items), then compare counts or read most_common. Valid Anagram.
    • "same in some way" groupsGrouping by a canonical key: build one label that is equal for every member, such as "".join(sorted(w)), then groups[key].append(w). Group Anagrams.
    • a partner that completes meComplement lookup in a dict: store value : index, ask for target - x before storing x. Two Sum.
    • values fit in 0..n, or counts are at most nIndex-as-hash or buckets: the array position is the key. Mark nums[v - 1] to say "v was seen", or put items in buckets[count] to sort by frequency in O(n). Top K Frequent, First Missing Positive.
  4. InvariantBefore you look at item i, everything before i is in the map, and nothing from i onwards is. So one lookup answers a question about the whole prefix.
  5. StepsMake the empty map. Loop once over the items. For each item, build its key, ask the map, answer or stop if the lookup says so, then store the item. After the loop, return the "not found" answer or read the map.
  6. CheckDid you ask before you stored? Otherwise an item can pair with itself, as in Trap 1.
  7. CheckIs every lookup on a set or dict, not a list? x in my_list quietly makes the loop O(n2).
  8. CheckIs the key hashable and truly the same for every member of a group? Use a tuple or a sorted string, never a list.
  9. CheckEdge inputs: an empty list, one item, all items equal, negative numbers, and a repeat at the very last position.
Rule to rememberName the lookup first, then the key, then the variant. The code is almost always the same five lines.

5. Two templates cover most of this pattern

Template A: the one-pass "seen" scan

Use it for "have I seen this?" and "is there a partner for this item?". This is the scan you watched in section 1.

CodeWhat it means
def has_repeat(nums):Answer: does any number appear twice?
seen = set()An empty coat check. Use {} instead when you need a value per key, such as an index.
for x in nums:One pass, left to right. Each item is visited once: O(n).
if x in seen:Ask first: "is x already here?" One glance, O(1) on average.
return TrueFound an earlier copy. Stop right away.
seen.add(x)Then remember x, so later items can find it.
return FalseReached the end with no repeat.

Cost: O(n) time, O(n) extra memory for seen.

Template B: count or group with a key

Use it for "how many of each?" and "put things that are the same in some way together".

CodeWhat it means
from collections import Counter, defaultdictTwo helpers from Python's standard library.
counts = Counter("banana")One pass that tallies each letter: key = letter, value = how many.
counts.most_common(1)The most frequent item and its count.
groups = defaultdict(list)A dict whose missing keys start as an empty list.
for w in words:One pass over the words.
key = "".join(sorted(w))Make a label that is the same for every word in a group: its letters in order.
groups[key].append(w)Drop the word into its group's bucket.

The real output from measure.py on small inputs:

# == 5. Templates on small inputs ==
Counter('banana') = Counter({'a': 3, 'n': 2, 'b': 1})
most_common(1)    = [('a', 3)]
groups            = {'opst': ['stop', 'pots', 'tops'], 'act': ['cat', 'act'], 'dgo': ['dog']}   # words = stop, pots, cat, tops, act, dog
Rule to rememberThe art of this pattern is choosing the key. Same key means "the same thing" for your problem: the number itself, a partner you need, or a sorted label.

6. Spot the pattern: does a hash map help here?

Read each made-up task. Decide yes or no, and name the clue. Then reveal.

A. A library logs book IDs as books come back. Report the first ID that comes back twice.

Yes. Signal: "have I seen this before?" Template A with a set.

B. Count how often each word appears in a speech, and return the most used word.

Yes. Signal: counting things. Counter(words).most_common(1).

C. Prices are sorted from low to high. Find two prices that add up to exactly 50, using only O(1) extra memory.

No, not this pattern. Signals: the input is sorted, and the memory limit forbids a big dict. That points to two pointers, one at each end (a later pattern). A dict would work, but it breaks the memory rule.

D. Shoppers list their basket items in any order. Put shoppers with exactly the same items into the same group.

Yes. Signal: grouping things that are "the same" in some way. Key = tuple(sorted(basket)), then Template B.

E. Daily temperatures are in a list. Find the longest run of back-to-back days above 20 degrees.

No, not this pattern. Signal: a contiguous run (back-to-back days). Nothing needs looking up; a single scan with a running length works. Runs like this are the sliding window family.

F. Two friends each list their favourite films. List the films both of them chose.

Yes. Signal: "is this item in the other list?" Put one list in a set, then check each film of the other. Comparing every pair would be O(n2).

Trigger signals"Seen before?", counting, grouping by "same in some way", finding a partner that adds up to a target, and an O(n) goal where O(n2) is the obvious idea.

7. Three classic traps

Trap 1: remembering before asking

Say you look for two numbers that add up to 10. If you store x before you ask "is 10 - x stored?", then 5 finds itself. Ask first, then store.

# == 6. Trap: check after insert (pair target 10) ==
buggy([5, 3], 10) = [0, 0]   # 5 paired with itself
fixed([5, 3], 10) = None
Trap 2: a list where a set was needed

x in my_list walks the whole list: O(n). Inside a loop that makes the whole thing O(n2), even though the code looks short. x in my_set is one jump. Timed with timeit, looking for a value that is not there (us = microseconds, ns = nanoseconds, per lookup):

# == 7. Trap: `in` on a list vs a set (value not present = worst case) ==
machine: Apple M5, Darwin arm64, Python 3.10.20
n =  10000: list   31.5 us   set 25.3 ns   list/set = 1,247x
n = 100000: list  320.4 us   set 26.8 ns   list/set = 11,950x

Ten times more items made the list about ten times slower. The set did not change. Your own laptop gives different numbers, but the same shape.

Trap 3: a key that can change

A list can change after you store it, so Python refuses it as a key. Turn it into a tuple, or into a sorted string for words.

# == 8. Trap: unhashable key ==
{[1, 2]: 'x'} -> TypeError: unhashable type: 'list'
{(1, 2): 'x'} -> {(1, 2): 'x'}
''.join(sorted('pots')) -> 'opst'
Rule to rememberAsk, then store. Use a set or dict for lookups, never a list. Keys are numbers, strings or tuples.

9. Your lesson's questions

Q1. The seen-it scan runs on [2, 7, 2]. How many times does if x in seen run before it returns True?

3 times. 2 is new, 7 is new, then the second 2 is found. measure.py prints (True, 3).

Q2. A list of 2000 numbers has no repeats. How many pair comparisons does the brute force make? How many steps does the seen-it scan make?

1,999,000 comparisons (2000 x 1999 / 2) against 2000 steps: about 1000 times more work. Double n from 1000 and the pair count goes up 4 times (from 499,500); the scan only doubles. Both numbers are printed by measure.py.

Q3. You want to group words that use the same letters. Why does groups[list(w)] fail, and what key works?

A list is not hashable (it can change), so Python raises TypeError: unhashable type: 'list'. It is also the wrong label: list("tops") and list("stop") differ. Use "".join(sorted(w)) or tuple(sorted(w)), which is the same for every word in a group.

Glossary: new words from this lesson

brute force
The obvious method that tries everything, such as comparing every pair. Correct, often too slow.
Big-O
A label for how the work grows as the input size n grows, ignoring constant factors.
O(1), O(n), O(n^2)
Constant (does not grow), linear (grows with n), quadratic (grows with n x n).
worst case
The input that makes a method work hardest; Big-O usually describes it.
hash map / dict
Stores values under keys and finds them by jumping to a slot: O(1) on average.
set
A hash map with keys only. Answers "is x here?" in O(1) on average.
key / value
What you look things up by / what is stored under it.
hash
A number made from a key that picks the slot.
collision
Two keys land on one slot; Python tries another, so O(1) holds on average, not always.
Counter
A dict that counts how many times each item appears.
defaultdict
A dict whose missing keys start with a default, such as an empty list.
hashable
Usable as a key because it cannot change: int, str, tuple. Not list, dict or set.

Recap: the pattern card in one minute

Idea: trade memory for time. Keep what you have seen in a set or dict, so each later question is one O(1) average lookup instead of an O(n) search.

Signals: "seen before?", counting, grouping things that are the same in some way, a partner that adds up to a target, and O(n) wanted where O(n2) is obvious.

Template A: seen = set(); for each x: if x in seen answer; then seen.add(x). Ask first, store second. Template B: Counter(items) to count; groups[key].append(x) with a hashable key to group.

Cost: O(n) time and O(n) extra memory. Brute force pair checking is O(n2): 499,500 comparisons against 1000 steps at n = 1000.

Traps: storing before asking; in on a list (O(n)); lists as keys (use a tuple or a sorted string).
